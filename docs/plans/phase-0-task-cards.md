# Phase 0：三人开发任务卡

依据：仓库根目录 mainbook.md 第 7、9、17、18 章与第 20 章 Phase 0。

状态：三张卡已编写，均待领取；尚未分配给具体姓名或开始实现。A、B、C 是角色代号。B 兼任本阶段集成协调人，具体姓名领取时登记。三人共同完成 Phase 0 验收后进入 Phase 1。

## 共同目标与开工顺序

交付可启动、可测试、可复现的前后端工程基础，使浏览器、API、PostgreSQL、Redis 和 Worker 连通。课程、登录、AI 模型调用、OCR、知识图谱属于后续阶段。

1. B 先核对并组织保存共同规格基线。当前 mainbook.md 的完整正文仍在未提交修改中，而 HEAD 中该文件为空；各人创建 worktree 前必须确保修订规格已进入共同基线，不能丢弃或覆盖现有修改。Git 仓库已经初始化，无需重新初始化或更换远端。
2. 三人使用同一基线提交号领取任务，分别建立 codex/phase0-a-frontend、codex/phase0-b-backend、codex/phase0-c-infra 分支和独立 worktree。仅在明确获得远端推送授权后推送。
3. B 先发布健康检查的响应示例及后端启动、测试、Worker 命令；A 发布前端启动、构建和测试命令。C 先提供可单独启动的 PostgreSQL、Redis 服务供 B 验证，再据 A、B 的入口完成整套容器与 CI，避免相互等待。三人可先按下列约定实现各自骨架。
4. B 先集成后端基础，再集成 A 的前端和 C 的基础设施。每次集成均基于明确提交号验证；CI 必须跟随源码使用同一套命令。

## 共享接口与运行约定

以下均为 Phase 0 的拟建路径和接口；目前尚无应用代码。框架和工具版本在执行时核对官方文档、锁定兼容版本并写入锁文件与运行文档。

| 项目 | 三方约定 |
| --- | --- |
| 工程目录 | frontend/ 为 Next.js + TypeScript；backend/ 为 FastAPI + SQLAlchemy + Alembic + Celery |
| 容器服务名 | frontend、backend、postgres、redis、worker、storage；storage 为开发用 S3 兼容服务 |
| 默认宿主端口 | frontend 3000、backend 8000；数据库和 Redis 默认仅内部网络访问；占用时通过环境配置调整 |
| GET /api/v1/health | 存活检查；HTTP 200，success=true，data.status="ok"，error=null；不依赖数据库或 Redis |
| GET /api/v1/ready | 就绪检查；数据库与 Redis 连通返回 HTTP 200，data 中含 status="ready"、database="ok"、redis="ok" |
| 依赖不可用 | ready 返回 HTTP 503，success=false，data=null，error.code="DEPENDENCY_UNAVAILABLE"；details 只给组件状态，不暴露连接串或密钥 |
| 浏览器访问 | A 提供同源 health/ready 转发路由；只在服务端读取 BACKEND_INTERNAL_URL，浏览器不接触容器内部地址或服务凭据 |
| 转发失败 | 上游不可达时由 A 返回 HTTP 502、error.code="UPSTREAM_UNAVAILABLE"；上游 503 保留原状态及响应结构；请求使用有限超时且不缓存 |
| 环境配置 | C 维护根 .env.example，覆盖 mainbook 要求的变量及 BACKEND_INTERNAL_URL 等实际启动变量；前后端分别校验自己的配置 |
| 本地与容器地址 | 宿主开发时使用本机地址；容器间使用服务名；C 在运行文档中区分这两种配置 |
| 数据库迁移 | B 独占 backend/ 下的模型和迁移；Phase 0 建立并验证迁移链，不提前创建后续业务表 |
| 后台任务 | B 提供独立 Celery 入口及无业务副作用的 smoke 任务；C 配置 worker 进程、Redis broker/backend 与运行检查 |
| 文件存储 | C 配置本地开发 S3 服务及隔离测试桶，验证写入、读取与删除测试对象；用户上传 API 留到 Phase 1 |

成功响应统一为 {"success":true,"data":{},"error":null}，错误响应遵循 mainbook 第 9 章。A 不再定义另一套健康响应格式。

- 浏览器请求与页面内容均不泄露内部服务地址、连接串或密钥。

## P0-B：后端、数据库与阶段集成

- 负责人：B（待领取）；评审人：C。
- 分支：codex/phase0-b-backend。

- 依赖：共同规格基线；本地就绪与任务验收需要 C 提供的 PostgreSQL、Redis 服务，或同配置的独立测试实例。

交付任务：

1. 组织保存三人共同规格基线，记录基线 SHA；冻结本卡共享接口与最小环境配置，将示例和命令交给 A、C。
2. 建立 FastAPI 与配置入口，实现 health、ready；数据库与 Redis 检查采用有限超时。
3. 配置 SQLAlchemy、数据库会话生命周期、Alembic 和最小迁移链；关闭时释放连接资源，数据库配置不散落到路由代码中。
4. 建立 Celery 应用入口、可独立启动的 worker 和无业务副作用的 smoke 任务，明确任务结果和超时读取方式；不导入 Web 进程启动副作用。
5. 提供 API 响应、依赖不可用及迁移/数据库连通的测试和运行说明。测试使用可控依赖，并执行真实 PostgreSQL、Redis 的集成检查。

验收条件：

- 后端启动、测试和迁移命令正常；在空的隔离数据库执行迁移成功，再次执行无重复影响。
- health 不受数据库或 Redis 不可用影响；ready 在正常、连接失败和超时场景返回约定结果。
- API、Worker 可独立启动；smoke 任务经 Redis 投递，由 Worker 消费并读到预期结果。
- 日志和健康响应不暴露敏感配置；Web 与 Worker 停止后无残留任务进程或未释放客户端。
- 数据与业务状态仍归后端服务所有，前端及任务基础设施没有直接修改业务状态的入口。

## 协作、解耦与完成门槛

文件归属以各卡范围为准。需要跨范围修改时由所属负责人实施，或先在 workbook 明确转交；接口变化同步三张卡及受影响实现。workbook 允许各人精确更新自己的记录，保留他人的活动条目。任务卡正文由协调人维护，领取人只登记自身状态。

解耦约定：浏览器 → Next.js 同源转发 → FastAPI → 数据库/Redis 连接层；基础设施只组合进程和配置。Celery 与 API 复用明确的配置入口，通过独立入口启动；业务路由不依赖具体容器名称或 CI。数据库、Redis、存储客户端由所属模块创建并关闭，配置可替换，超时与异常不泄露凭据。后续 AI 适配层不得直接控制业务数据库。

每卡交付前检查实际 diff、调用方、配置和取消/关闭路径，对照上述约定记录“通过 / 有保留项 / 未通过 / 未验证”及证据；功能测试与解耦结论分开。此文档只定义未来验收，未验证任何实现。
